# Product Delight

Work within the selected or named scope and the user's request. Review requests produce findings without edits; implement changes when requested. Use available context, disclose inaccessible evidence, and preserve unrelated work.

Delight comes from anticipation, reliability, and care. Motion can support those qualities, but adding animation is not the same as improving the experience.

## Find the need

Start with the person and task in the supplied brief or selected flow. Infer reasonable context; ask only when missing information would change the design materially.

Look first for avoidable uncertainty: a useful default, preserved input, clear next step, timely feedback, recoverable mistake, or considerate empty state. Fix the base experience before adding celebration.

## Choose a small improvement

- Anticipate what someone will need next without removing their control.
- Reuse available context to reduce unnecessary setup or repeated entry.
- Answer important questions about progress, outcome, and recovery.
- Prefer one meaningful moment over competing flourishes.
- Use motion to connect cause and effect.
- Evaluate the second and tenth use, not only the first impression.
- Remove novelty that delays the task or competes with content.

## Figma Design

Use the existing visual system and components. Show the state before the improvement, the response, and any recovery state needed to explain the interaction. Keep scope within the requested flow.

Prototype feedback when supported and annotate persistence, latency, or failure behavior that the canvas cannot demonstrate. A prefilled mock value does not establish a working contextual default.

## Make

Connect feedback to actual state transitions rather than a timer that always reports success. Preserve user input during recoverable failure, prevent accidental repeated submissions where needed, and keep useful actions available under slower responses.

Use representative empty, pending, success, and failure states when data is simulated. Identify simulation clearly. Do not claim real reliability or persistence from a rehearsed happy path.

## Verify

Exercise the underlying task, repeated use, interruption, and available failure scenarios. Check touch, keyboard, and a reduced-motion equivalent when applicable.

Explain what need the improvement addresses. If removing a flourish makes the product only quieter, consider removing it. Report observed behavior separately from intended production behavior.
