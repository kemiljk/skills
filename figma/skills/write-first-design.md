# Write-First Design

Work within the selected or named scope and the user's request. Review requests produce findings without edits; implement changes when requested. Use available context, disclose inaccessible evidence, and preserve unrelated work.

Use prose to resolve uncertain decisions while changes are cheap. A clear brief or narrowly specified edit already gives direction; do not add an unnecessary briefing or approval ritual.

## Decide whether writing helps

Read the supplied request and available design context. If the intended outcome is clear, proceed with the requested work. For substantial ambiguous work, briefly state:

- Who is trying to do what.
- The proposed change and why it should help.
- The behavior or outcome that would make the change successful.
- Any non-goals or unresolved choices that meaningfully constrain the work.

A useful hypothesis is “We believe this change will produce this outcome because of this reason.” Adapt the wording rather than filling a rigid template.

## Resolve decisions proportionally

Ask only about missing choices that would materially change the result. Otherwise state a reasonable assumption and continue within the authorized scope.

Explain consequential tradeoffs before investing in expensive visual or implementation detail. Avoid long process documents for small changes and do not turn a design rationale into an invented user requirement.

## Work in Figma

Keep the brief in the response or an existing design decision area. Add a new canvas note only when it helps the requested deliverable. Do not create a separate document or file structure merely to satisfy a process.

For Figma Design, connect the rationale to the selected flow, key states, content, and layout decisions. For Make, connect it to the behavior implemented in the running prototype and distinguish real functionality from simulation.

Update the rationale when building reveals a different tradeoff. Keep open decisions explicit instead of rewriting uncertainty as certainty.

## Complete the requested outcome

If the user requested a brief, deliver a concise brief that supports a decision. If they requested implementation, use the brief to guide the design or build and continue through relevant verification.

Report the result and material limits. A design illustrates intent; a runtime test establishes only the behavior actually exercised. Do not describe proposed outcomes as measured results.
